# 길동무 구조와 개발 과정

디자인(화면 모양)은 뺀 개발 쪽 구조입니다. 쓴 것은 코드와 테스트로 확인한 것이고, 안 한 것은 안 했다고 적었습니다.

## 1. 큰 틀

```
 차량 앱 (Kotlin, Pleos Connect 에뮬레이터)              서버 (Python, 표준 라이브러리만)
┌─────────────────────────────────────────┐   HTTP    ┌──────────────────────────────────┐
│ MainActivity   화면 흐름·주행/정차 판단     │  JSON    │ app_server.py  라우팅·폴링·동기화    │
│ RoadView       도로·차 그리기              │ ◀──────▶ │ core.py        차량 위치·반경 탐색    │
│ Errands        픽업 데이터·말 해석          │          │ questions/chat 질문·말풍선        │
│ ApiClient      서버 호출                   │          │ board.py       도로 소식·점수·등급    │
│ NaviClient     Pleos NaviHelper           │          │ hazards.py     위험 신고·사진(디스크)  │
│ PleosClients   Pleos Vehicle·FusedLocation│          │ shops.py       가게 등록·주문(디스크)  │
│ DrivingMonitor 속도·주행 규제(AAOS)         │          │ live.py        폰 이웃·프로필 목록    │
│ HazardCamera   사진 한 장                  │          └───────────────┬──────────────────┘
│ VoiceInput     안드로이드 음성 인식         │                          │
└─────────────────────────────────────────┘          브라우저 화면: /neighbor(이웃) /shop(가게) /ask
```
- 앱은 서버를 3초(이웃·질문)·10초(가게·주문) 간격으로 조회하는 **폴링** 구조입니다. 실시간 푸시는 아직 없습니다.
- 서버는 **시험용**(내 PC, 인증·TLS 없음)입니다. 누구나 가게를 등록할 수 있는 상태입니다.

## 2. 개발한 순서 (블로그의 일반적인 단계와 비교)
| 단계 | 실제로 한 일 | 안 한 것 |
|---|---|---|
| 아이디어 구체화 | 정체·휴게소에서 정보가 없다는 문제 정의, 이웃 질문·위험 알림·가는 길 픽업으로 기능 정리 | 실제 사용자 인터뷰·경쟁 앱 수치 조사(보도 기준 시장 근거만 있음) |
| 기획 | 주행·정차에 따른 입력 제한 원칙, 기능별 데이터 구조, 심사 기준에 맞춘 기획서 | 스토리보드·Figma 사용자 흐름도(디자이너 합류 후) |
| 기술 선택 | Kotlin 앱 + Python 서버 + SQLite(신고·주문), Pleos NaviHelper·Vehicle·FusedLocation SDK | 로그인·클라우드 배포(Firebase/AWS 등) |
| 개발 | 서버 먼저(`core`→`questions`→`board`→`hazards`→`shops`), 앱은 에뮬레이터로 확인하며 기능 추가 | 앱 구조 분리(MainActivity 한 파일이 2,400줄) |
| 테스트 | 서버 자동 테스트 113개, 앱 단위 테스트, 에뮬레이터 화면 확인, 이웃 시험 클라이언트(`tools/neighbor_demo.py`) | 실제 차량, 에뮬레이터 두 대 동시, 폰 마이크 인식, 부하 시험 |

## 4. 가는 길 픽업·결제의 흐름
1. **가게 등록:** 가게가 `POST /api/shops/register`로 이름·브랜드·종류·위치·전화·준비 시간·메뉴(음료/식사/간식)를 보냅니다.
2. **조회:** 앱이 차 위치로 `GET /api/shops?lat&lon`을 부르면 5km 안 가게가 거리·도착 시간과 함께 옵니다.
3. **제안:** 말("커피 마시고 싶어") 또는 버튼으로 종류를 고르면 가장 가까운 한 곳과 메뉴 하나를 보여 주고, 메뉴는 말·터치로 바꿀 수 있습니다.
4. **결제:** `POST /api/shops/order`(서버가 가격을 정하고 같은 탭은 한 주문으로 처리). 결제는 **모의**(등록 카드 ****1234)입니다.
5. **진행:** 가게 화면(`/shop`)이 `수락 → 조리 시작 → 준비 완료 → 수령`으로 진행시키고, 차는 `GET /api/shops/order?receipt&lat&lon`으로 따라갑니다. 차가 막혀 멀어지면 도착 시간이 늦춰지고 가게 화면에 "막혀서 +N분"이 뜹니다. 조리 시작 전까지는 차에서 취소할 수 있습니다.
6. **안 한 것:** 실제 결제·지문 인증, 가게에 실제 전달, 가게 로그인, 가게별 메뉴 품절 관리.

## 5. 알려진 한계
- 서버 인증·TLS 없음, 게시판·질문·점수는 서버를 껐다 켜면 사라짐(신고·주문·가게는 디스크).
- 폴링 구조라 이웃 수가 많아지면 서버 부하가 커짐(격자 인덱스로 2만 대 조회 1.6ms는 측정했으나, 실제 접속 부하 시험은 안 함).
- `MainActivity.kt`가 2,400줄이라 여러 명이 동시에 고치면 충돌하기 쉬움 → 기능별 파일로 나누는 작업이 먼저 필요(`docs/TEAM.md`).

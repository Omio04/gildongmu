# 가는 길 픽업·결제: 가게와 어떻게 연동되고, 결제는 어떻게 되는가

PT에서 "이게 실제로 어떻게 돌아가나요?"라는 질문에 답하기 위한 설명입니다. **지금 만든 것**과 **실제 서비스라면 필요한 것**을 나눠 적었습니다.

## 한눈에
```
가게(제휴 가입) ──등록──▶ 길동무 서버 ◀──조회──  차량 앱 ──결제 요청──▶ (결제대행사)
   ▲  주문 화면(/shop)        │  주문 기록·진행 상태        │ 결제 수단은 미리 등록(토큰만 차에 보관)
   └────── 수락·조리·준비 ─────┘◀── 위치로 도착 시간 갱신 ──┘
```

## 0. 폰 앱과의 차이 (질문받았을 때의 답)
"폰 주문 앱을 대체하려는 게 아니라 **운전 중이라 폰을 못 쓰는 순간**을 메웁니다. 그리고 **차만 아는 정보**로 주문 시점을 맞춥니다."
- 차가 먼저 묻습니다(정체로 서 있을 때, 도착 10~25분 전). 폰은 앱을 열어야 시작합니다.
- 주문한 가게를 **차 내비의 경유지로 넣고**, 내비가 계산한 **실제 길 시간**으로 가게의 조리 시작을 맞춥니다(직선거리 추정이 아님).
- 말 세 마디로 끝나고, 주행 중에는 터치를 막습니다. 기어·속도는 Pleos Vehicle SDK와 차량 API에서 읽습니다.
- 한계: 결제·가게는 모의, 말 세 마디의 실제 소요 시간은 미측정, 내비 경유지 추가는 NAVI_ROUTE_SEARCH 권한이 필요한데 현재 디버그 빌드에만 있어 앱마켓 심사 승인 여부는 미확인.

## 1. 가게는 어떻게 이 서비스에 들어오는가
| 단계 | 실제 서비스라면 | 지금 구현된 것 |
|---|---|---|
| 가입 | 가게가 제휴 신청(사업자 확인, 정산 계좌 등록) | **미구현** (서버에 누구나 등록 가능한 시험 상태) |
| 정보 등록 | 가게가 이름·브랜드·종류·위치·전화·준비 시간·메뉴(음료/식사/간식, 가격)를 구조체로 등록 | **구현**: `POST /api/shops/register`, 가게 화면 `/shop`의 등록 폼 |
| 노출 | 차의 위치 5km 안 가게만 앱에 표시, 앱은 가게가 보낸 데이터를 그대로 읽음 | **구현**: `GET /api/shops?lat&lon` |
| 주문 받기 | 가게 화면·단말에 주문이 실시간으로 뜸 | **구현**: 가게 화면이 2초마다 갱신, 수락·조리 시작·준비 완료·수령 버튼 |
| 정산 | 주문 금액에서 수수료를 떼고 가게에 정산 | **미구현**(확장 방향, 수수료율은 협의 필요) |

가게 정보는 앱에 박아 두지 않고 서버에 있습니다. 새 가게가 등록되면 앱을 고치지 않아도 차가 가까워질 때 나옵니다.

## 2. 결제는 어떻게 되는가
**원칙:** 카드 번호는 차에도, 길동무 서버에도 없습니다. 차가 가진 것은 결제대행사(PG)가 카드 등록 뒤 돌려주는 **토큰**뿐입니다.

1. **미리 등록(정차 중, 한 번):** 폰이나 웹에서 카드사 화면으로 카드를 등록하면 PG가 토큰을 발급하고, 차량 앱은 그 토큰만 보관합니다.
2. **주문 때:** 앱이 "가게, 메뉴, 토큰"을 서버로 보냅니다. **가격은 서버가 가게 메뉴에서 정하고** 앱이 보낸 금액은 믿지 않습니다.
3. **확인:** 주행 중에는 음성("결제"), 정차 중에는 큰 버튼 한 번. 실제 서비스에서는 여기에 본인 확인(PIN·지문·음성 인증 등)과 1회 한도를 붙입니다.
4. **승인과 정산:** 서버가 PG에 승인을 요청하고, 성공하면 주문이 가게에 전달됩니다. 정산은 PG에서 가게로 이뤄집니다.
5. **취소·환불:** 조리 시작 전까지 차에서 취소(전액 환불), 조리 시작 뒤에는 가게에 전화(가게 사정에 따름).

| 항목 | 지금 구현된 것 | 안 한 것 |
|---|---|---|
| 결제 수단 등록 | 앱에서 **모의 등록**(가짜 토큰 `tok_…`, 카드 ****1234 표시). 프로필 카드와 주문 카드에서 등록·삭제, 주행 중에는 등록 불가(음성으로 "먼저 등록해 주세요" 안내) | 실제 카드사 화면, PG 연동 |
| 서버의 토큰 검사 | 토큰 형식이 아니면 주문 거절(카드 번호처럼 생긴 값도 거절), 같은 탭 재전송은 한 주문 | 토큰 유효성·한도 확인 |
| 가격 결정 | **서버가 결정** | |
| 승인·정산·환불 | **미구현** (주문에는 "모의 결제"라고 기록) | PG 승인, 정산, 환불 |
| 본인 확인 | **미구현** (지문·PIN은 제조사 결제 연동이 필요) | |

## 3. 주문 뒤의 진행 (구현함)
`접수됨 → 가게가 수락 → 조리 중 → 준비 완료 → 수령 완료`(또는 취소). 차는 `GET /api/shops/order`로 따라가고, **차의 위치를 서버가 받아 도착 시간을 다시 계산**합니다. 길이 막혀 늦어지면 가게 화면에 "차가 막혀서 +N분 늦어요"가 뜨고 조리 시작 시점이 뒤로 밀립니다. 상태가 바뀌면 앱이 음성으로 알려 줍니다. 조리를 시작하면 차에서는 취소할 수 없고 가게에 전화(☎ 번호는 가게 데이터)합니다.

## 4. 개인정보와 안전
- 서버에 남는 것: 가게, 주문(메뉴·가격·접수번호·도착 시간·결제 토큰 앞 8자리), 주문한 차의 위치는 도착 시간 계산에만 쓰고 이웃에게 보이지 않습니다.
- 주행 중에는 카드 등록과 터치 결제를 막고 음성으로만 진행합니다.
- 동의 화면에 "주문(가게·메뉴·접수번호)만 서버에 기록돼요. 시험용이라 실제 결제는 되지 않아요"를 적어 두었습니다.

## 5. 실제 서비스로 가려면 (우선순위)
1. 결제대행사 연동(토큰 발급·승인·환불)과 본인 확인 방식 결정(제조사 결제 서비스 연동 가능 여부 확인)
2. 가게 가입·로그인(주문 화면 접근 제한), 정산 구조와 수수료 협의
3. 서버 인증·TLS, 주문 알림을 폴링 대신 푸시로
